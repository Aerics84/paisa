    Svelte 5 conventions¶

    This project runs Svelte 5 in legacy-compatible mode while the frontend migrates to runes. New and touched components follow the rules below. During the migration batches (Tasks 4.4/4.5) no component behavior changes; only the syntax moves.

    Ratchet¶

    scripts/check-runes.mjs counts legacy syntax in src/**/*.svelte and compares it with scripts/runes-budget.json:

    Metric Meaning
    export let legacy component props
    $: legacy reactive statements
    on:click legacy event directive
    createEventDispatcher legacy component event dispatcher 
    npm run check:runes

    The command prints the current counts and fails when a count exceeds its budget. CI runs it after the other gates.

    The count is textual and line-based, not an AST analysis. Only on:click is tracked; other on: event directives are unguarded, and a net-zero swap (one usage removed while another is added) passes. Treat the gate as a guard-rail, not as proof that the migration is complete.

    Budgets only go down. After a migration batch, lower them to the measured counts:

    npm run check:runes -- --update-budget

    The flag refuses to raise a budget; a count above its budget must be migrated, not budgeted. The counts are measured at the merge base of this task; do not copy older numbers from planning documents.

    Props: export let → $props()¶

    <!-- before -->
<script lang="ts">
  export let label: string;
  export let value = 0;
</script>

<!-- after -->
<script lang="ts">
  interface Props {
    label: string;
    value?: number;
  }

  let { label, value = 0 }: Props = $props();
</script>

    Keep the same defaults and optionality. Type the destructured object with a Props interface instead of loose annotations.

    Two-way bindings: $bindable()¶

    Props that parents set with bind: must be declared with $bindable():

    <!-- before -->
<script lang="ts">
  export let value = 0;
</script>
<input type="number" bind:value />

<!-- after -->
<script lang="ts">
  interface Props {
    value?: number;
  }

  let { value = $bindable(0) }: Props = $props();
</script>
<input type="number" bind:value />

    Only mark a prop as bindable when the component writes back to it. Regular one-way props stay plain destructured values.

    Local state: $state¶

    Using $props() puts the component in runes mode. Plain local let is then no longer reactive when markup reads it; handlers must write a $state value.

    <!-- before -->
<script lang="ts">
  let open = false;
</script>
<button on:click={() => (open = !open)}>Toggle</button>
{#if open}<p>Panel</p>{/if}

<!-- after -->
<script lang="ts">
  let open = $state(false);
</script>
<button onclick={() => (open = !open)}>Toggle</button>
{#if open}<p>Panel</p>{/if}

    Objects and arrays mutated in place also need $state; use $state.raw(...) only for values that are always replaced wholesale. This applies even when the state is read by an $effect only.

    Derived values: $: → $derived¶

    <!-- before -->
<script lang="ts">
  export let amount = 0;
  export let taxRate = 0;
  $: tax = amount * taxRate;
  $: total = amount + tax;
</script>

<!-- after -->
<script lang="ts">
  interface Props {
    amount?: number;
    taxRate?: number;
  }

  let { amount = 0, taxRate = 0 }: Props = $props();
  let tax = $derived(amount * taxRate);
  let total = $derived(amount + tax);
</script>

    For multi-statement derivations use $derived.by(() => { ... }). Derived values are pure calculations; do not assign to them.

    If a $: statement reads state and is also assigned by handlers, it is not a pure derivation: a $derived value cannot be written. Keep it in $state and assign in the handler, or use $state plus $effect when the assignment must react to several inputs. See Local state.

    Side effects: $: → $effect¶

    <!-- before -->
<script lang="ts">
  export let chartData;
  export let renderer;
  $: if (renderer) {
    renderer.draw(chartData);
  }
</script>

<!-- after -->
<script lang="ts">
  interface Props {
    chartData: unknown;
    renderer?: { draw: (data: unknown) => void };
  }

  let { chartData, renderer }: Props = $props();

  $effect(() => {
    renderer?.draw(chartData);
  });
</script>

    Use $effect only for imperative side effects (charts, DOM integration, subscriptions). Do not use it to keep a second copy of state in sync; that is a $derived value. Return a cleanup function for subscriptions and observers.

    Events: on:event → onevent¶

    <!-- before -->
<button on:click={() => (open = true)}>Open</button>
<button on:click|preventDefault={submit}>Save</button>

<!-- after -->
<button onclick={() => (open = true)}>Open</button>
<button
  onclick={(event) => {
    event.preventDefault();
    submit();
  }}
>
  Save
</button>

    Modifiers become explicit code in the handler. Component listeners follow the same pattern: on:change becomes onchange, plus the matching callback prop below. The ratchet currently tracks on:click; all on: directives are migrated the same way.

    |capture and |once cannot be expressed as inline code alone. Keep an explicit addEventListener(..., { capture: true }) or { once: true } (for example inside $effect); do not approximate them by calling the handler once.

    Component events: createEventDispatcher → callback props¶

    <!-- before -->
<script lang="ts">
  import { createEventDispatcher } from "svelte";

  const dispatch = createEventDispatcher<{ change: string }>();
</script>
<button on:click={() => dispatch("change", value)}>Pick</button>

<!-- after -->
<script lang="ts">
  interface Props {
    onchange?: (value: string) => void;
  }

  let { onchange }: Props = $props();
</script>
<button onclick={() => onchange?.(value)}>Pick</button>

    The parent passes a function instead of listening to an event:

    <Picker onchange={(value) => (selected = value)} />

    Callback props are optional (onchange?) unless every caller must handle the event. Call them with optional chaining so components without a listener keep working.

    Stores stay allowed¶

    Stores are not deprecated and are not part of the ratchet. Keep importing them and read them with the $store auto-subscription:

    <script lang="ts">
  import { selectedCurrency } from "$lib/store";
</script>

<p>{$selectedCurrency}</p>

    Do not rewrite the store modules during the runes migration. When a value is derived from a store, wrap the store read in $derived(...) like any other expression.

    Typing¶

    • No new any in new or migrated components. Use a Props interface and concrete types for callback props.
    • Callback props are functions: onchange?: (value: T) => void, not onchange?: Function.
    • Keep existing exported types and module imports unchanged unless the compiler requires a change.

    Conversion checklist¶

    1. Replace export let with a typed $props() destructure.
    2. Add $bindable() only for props written through bind:.
    3. Convert local let read by markup to $state(...); when a $: both reads state and is assigned by handlers, do not use plain $derived — use $state plus $effect or event-driven assignment.
    4. Replace $: value calculations with $derived/$derived.by.
    5. Replace $: side effects with $effect and clean up subscriptions.
    6. Replace on:event with onevent; inline modifiers explicitly and use addEventListener options for |capture/|once.
    7. Replace createEventDispatcher with callback props.
    8. Keep stores and behavior unchanged.
    9. Run npm run check:runes and, after the batch, --update-budget.
